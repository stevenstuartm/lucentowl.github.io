# Azure Study Guides Refinement Plan

Tracks the review-and-refine pass over all guides in `_guides/infrastructure/azure/`. Guides are consumed sequentially, in the order they appear in `assets/data/study_guides_config.json` (the "Azure" category) — that order already encodes the fundamentals-to-advanced learning path, so no guide should add its own prerequisite framing or cross-links to other Azure guides; the config ordering handles that.

**The checklist, the process rules, and the cross-domain gotchas live in [`.claude/content/guide-refinement-standard.md`](../.claude/content/guide-refinement-standard.md).** Read it first. This document carries only what is specific to the Azure pass: sources, domain gotchas, verified cross-guide facts, pre-flags, and the progress table.

## Sources

- Primary: [Microsoft Learn](https://learn.microsoft.com) and the official Azure product docs.
- Pricing: the Retail Prices API (see domain gotchas) — the `azure.microsoft.com` pricing pages are unreliable.
- Off-limits: marketing pages on `azure.microsoft.com` for any figure that will be asserted as fact. Several unverifiable claims in this pass trace to numbers that exist only there.

## Domain notes

**Item 7 (hierarchy and scope clarity)** in Azure means the management hierarchy — tenant → management group → subscription → resource group → resource — and the networking hierarchy — region → VNet → subnet → NIC. The canonical example of the gap: `azure-vnet-architecture.md`'s Application Security Groups section listed "All NICs in an ASG must be in the same VNet" as a constraint but never stated up front that ASGs are VNet-scoped, so a reader couldn't tell at a glance whether ASGs were a subscription-wide construct or something narrower.

**Item 9 (tag audit)** — measured across the 61 Azure guides before the pass: `azure` on 100%, `practical` on ~48, `infrastructure` on ~45, `cloud-computing` on ~35. So for this category: drop `azure` outright (redundant with the category), and treat `infrastructure` and `cloud-computing` as the filler tags to replace with real content signal. The specific nouns to reach for are services, patterns, and products — `aks`, `keda`, `gitops`, `service-mesh`, `workload-identity`, `cosmos-db`, `private-link` — not the vocabulary-table generics.

## Domain gotchas

- **`azure.microsoft.com` pricing pages time out; the Retail Prices API doesn't.** Rows 8, 10, and 11 all lost the pricing page to timeouts. `https://prices.azure.com/api/retail/prices?$filter=serviceName eq '<Service>' and armRegionName eq 'eastus' and type eq 'Consumption'` is public, unauthenticated, returns JSON, and is the same official rate data. Use it before flagging any pricing claim unverifiable. It has one failure mode: meters can be pre-registered for features that aren't shipped (row 11 found self-hosted-gateway meters on v2 tiers that three doc pages say don't exist), so it settles *prices*, not *feature availability* — cross-check the latter against docs.
- **Per-tier SLA percentages are not on MS Learn.** They live only in the SLA-for-Online-Services .docx, which WebFetch can't read, and the product docs deliberately say only "an SLA exists" and "zones or regions raise it." Don't assert 99.9x figures from memory; state has-SLA/no-SLA and link the SLA doc (row 11's pattern).
- **The archive-redirect tell in MS Learn's URL shape.** Learn moves an archived article under `learn.microsoft.com/previous-versions/azure/...` and stamps it `is_archived: true`; the live page then links back to it as "archived Classic API guidance." Watch also for `learn.microsoft.com/azure/<service-a>/<feature>` resolving to a canonical URL under `/azure/<service-b>/` — the feature moved services, usually to a different billing model and RBAC surface.
- **Azure docs are heavily zone-pivoted** between a legacy tier and the current one, and the two zones can describe architecturally different products. Confirm which pivot a claim came from. The FAQ often states a transition the concept pages don't.
- **Guides with heavy code still ahead:** none. Rows 60-61 are architecture guides; verify any Bicep or CLI snippets they contain as claims all the same.
- **Tier comparisons still ahead:** none remaining. Confirm the tier *count* and the tier *names* before refining any table that reappears.
- **Remaining sibling links to remove** (`grep -rn 'href="/study-guides/\|](/study-guides/' _guides/infrastructure/azure/`): none known on rows 58-61. Re-run the grep before closing the pass, and check both markdown links and `<a href>` inside HTML callouts.

## Cross-guide facts in force

Verified during earlier rows; applies to every remaining guide that touches the topic.

- **Front Door** Standard/Premium selects POPs by unicast via an internal Traffic Manager profile (changed Mar-Apr 2026). Anycast is classic-only.
- **gRPC through a layer-7 load balancer is Application Gateway for Containers, never Application Gateway.** App Gateway does not do HTTP/2 to backends.
- **APIM** gateway-to-backend HTTP/2 and pass-through gRPC are classic-only and in preview.
- **Azure Cache for Redis** is superseded by Azure Managed Redis. Any guide recommending a Redis tier needs the AMR migration path.
- **Service Bus** SBMP and the legacy SDKs (WindowsAzure.ServiceBus, Microsoft.Azure.ServiceBus, com.microsoft.azure.servicebus) retire **30 Sept 2026**.
- **Event Grid** dead-letters to a **blob container**, never a queue.
- **Durable Functions** docs moved to `learn.microsoft.com/azure/durable-task/` and are zone-pivoted between Durable Functions and the standalone Durable Task SDKs. Check which pivot a claim came from.
- **Azure CLI:** a JSON parameter file needs `--parameters @file.json`. The `@` marks it as a file. `.bicepparam` files take no `@`.
- **ARM complete mode** is documented as "will be gradually deprecated," with deployment stacks as the replacement.
- **Microsoft Sentinel** is unsupported in the Azure portal after **31 March 2027** and runs only in the Defender portal, where Defender XDR creates incidents and Microsoft-security and Fusion rule types are unavailable.
- **Log Analytics retention:** analytics retention 4-730 days plus total retention up to 12 years. The "1 day to 2 years" figure and the "archive tier" are both retired; long-term data comes back via search job.
- **Defender for Servers** no longer uses the Log Analytics agent or AMA except for the 500 MB ingestion benefit.
- **Azure Firewall has three SKUs** (Basic / Standard / Premium), not two. Basic caps at 250 Mbps, is threat-intelligence **alert-only**, and has no DNS proxy. Standard 30 Gbps, Premium 100 Gbps.
- **Azure Firewall rule order** is threat intelligence (highest priority, before any rule), then DNAT, then network, then application, then the built-in infrastructure rule collection, then default deny. Order is fixed by rule *type*, not by priority numbers. A network rule match terminates, so a broad `Allow 443 to Internet` network rule disables every application rule. Application rules never run on inbound connections and cover HTTP/HTTPS/MSSQL only, matching on Host header / SNI.
- **A Firewall Policy is shared,** attachable to many firewalls across regions and subscriptions. Free at zero or one association, billed at a fixed rate above that. Parent policy rule collection groups always outrank the child's; NAT rules are never inherited; threat-intel mode can only be overridden stricter.
- **Azure DDoS Protection is layer 3-4 only** and has three levels: free infrastructure protection, DDoS IP Protection ($199/IP/month US list), DDoS Network Protection (fixed plan fee covering 100 IPs). Break-even ~15 IPs. Rapid response (DRR), cost protection, and the App Gateway WAF discount are Network Protection only. Not supported on Virtual WAN, multi-tenant PaaS, or NAT Gateway public IPs. Thresholds are machine-learned and not user-configurable (custom policy is preview).
- **Virtual WAN secured hubs do not inspect spoke-to-spoke or inter-hub traffic** until **routing intent** is enabled. Firewall Manager manages Firewall Policy, DDoS plans, and WAF policies, never NSGs.
- **Key Vault access policies are NOT deprecated.** Both models stay fully supported. What has a date: from API version **2026-02-01** new vaults default to Azure RBAC, and **all control plane API versions before 2026-02-01 retire 27 Feb 2027** (needs Azure CLI 2.90.0+/Az PowerShell 16.3.0+). Any guide showing a Key Vault ARM/Bicep/Terraform resource needs its API version checked. The two models are exclusive: switching a vault to RBAC invalidates every access policy at once.
- **Every built-in Key Vault role is a DATA plane role**, including Key Vault Administrator ("cannot manage key vault resources"). `Key Vault Contributor` is the control-plane role and grants no data access. Vault firewall rules apply to the **data plane only**, so ARM/Bicep secret deployment through `management.azure.com` bypasses them.
- **Managed HSM is a separate resource type, not a vault tier**, and stores HSM keys only (no secrets, no certificates, no software keys). Vault tiers are Standard (FIPS 140-2 L1) and **Premium (FIPS 140-3 L3 on HSM Platform 2)**. Symmetric/AES (oct-HSM) keys are Managed HSM GA and Premium-vault **preview**, never Standard.
- **Azure Disk Encryption retires 15 Sept 2028**; ADE disks stop unlocking on reboot after that. Encryption at host is the replacement and the only option Defender for Cloud reports healthy. Any guide recommending ADE needs rewriting.
- **Key Vault soft delete cannot be disabled** once on; retention is 7-90 days (default 90), fixed **at vault creation**. Soft-deleting a vault also deletes its **RBAC role assignments and Event Grid subscriptions**, and recovery does not restore them. Key rotation **re-wraps DEKs, it does not re-encrypt data**. Secret `exp` is informational: a `get` on an expired secret still succeeds.
- **App Service/Functions cache Key Vault references and refetch every 24 hours.** Rotation is not picked up immediately without a config change, restart, or a POST to `config/configreferences/appsettings/refresh`.
- **Azure Blueprints retires 31 Jan 2027**, phased: 31 Jul 2026 no new definitions/versions, 31 Oct 2026 no definition edits and no new assignments, 31 Dec 2026 no assignment edits. Unexported definitions/versions/assignments are **permanently deleted** at retirement and blueprint **locks stop functioning**; deployed resources remain. Replacement is two features: **template specs (or Git)** for storage/versioning, **deployment stacks** for assignment, lifecycle, and deny-assignment locking.
- **Azure Policy has 11 effects** (addToNetworkGroup, append, audit, auditIfNotExists, deny, denyAction, deployIfNotExists, disabled, manual, modify, mutate) in a fixed evaluation order: disabled, append/modify, deny, audit, manual, auditIfNotExists, denyAction last; deployIfNotExists runs after the RP succeeds. Layering is **cumulative most restrictive** with no priority ranking. `denyAction` is the only effect that blocks deletion.
- **enforcementMode `DoNotEnforce`** is the correct dry run for a deny policy (audit is a different evaluation path). `Enroll` mode exists for staged opt-in. Assignments also carry `overrides`, `resourceSelectors`, `notScopes`, `nonComplianceMessages`, and `definitionVersion` pinning on built-ins.
- **Compliance % counts exempt + unknown + protected as compliant**, so exemptions inflate the score. Compliance states are Non-compliant, Compliant, Error, Conflicting, Exempt, Unknown, Protected, Not started, Not registered. Exemption categories are **Mitigated** (intent met another way) and **Waiver** (non-compliance accepted), not duration labels, and an exemption is **not deleted at expiry**.
- **deployIfNotExists/modify use two identities**: the caller's identity evaluates the existence condition, the assignment's managed identity performs the deployment. Existing resources need an explicit remediation task.
- **Defender for Cloud regulatory compliance beyond MCSB requires a paid Defender plan** (any except Servers P1 / API P1). Current standards are PCI DSS **v4.0.1**, ISO/IEC 27001:**2022**, NIST SP 800-53 **R5.1.1**, CIS Azure Foundations v2.1.0/v3.0 (v3.2.1-era names are stale). Non-auto-assessable controls are greyed out, not failed.
- **Management groups:** 10,000 per directory, **6 levels deep** (excluding root and subscriptions), one parent each. Root MG cannot be moved or deleted and needs Global Admin elevation. ARM caches the hierarchy up to **30 minutes**. A custom definition must be stored at or above its assignment scope.
- **Log Analytics retention is two settings:** analytics retention 4-730 days (default 30) and **total retention up to 12 years** (4,383 days), with long-term data reached via **search jobs**. **31 days are included in the ingestion price**, so cutting below 31 saves nothing. Table plans are **Analytics / Basic / Auxiliary**. `Usage`, `AzureActivity`, and all App Insights `App*` tables are free for 90 days. US East list: $2.30/GB ingestion, $0.10/GB/month retention.
- **Azure Monitor has four stores:** Azure Monitor Metrics (93 days, fixed, free), Log Analytics workspace (KQL), **Azure Monitor workspace** (a distinct resource type for managed Prometheus, PromQL, **18 months free**), and workspace-based Application Insights (physically inside Log Analytics). Container Insights = logs; Managed Prometheus = metrics.
- **Diagnostic settings never collect guest OS data.** Guest logs/perf require **AMA + a data collection rule**. DCR transformations filter before billing. The Log Analytics agent (MMA/OMS) is retired; Defender for Cloud uses only the Defender for Endpoint agent and Update Manager uses no agent.
- **Six alert types:** metric, log search, simple log search, activity log (**Resource Health and Service Health alerts are activity log alerts**), smart detection, Prometheus. **All activity log alerts are stateless.** Metric alerts resolve after 3 clear checks. **Metric alert rules are billed per monitored time series**, not free. Alert processing rules are the maintenance-window mechanism. Fired alerts are read-only, stored 30 days.
- **Application Insights instrumentation is OpenTelemetry.** The Azure Monitor OpenTelemetry Distro (`UseAzureMonitor()`) is the recommended path for ASP.NET Core, Java, Node.js, and Python; `Azure.Monitor.OpenTelemetry.Exporter` covers classic ASP.NET/console/WinForms; browsers stay on the Application Insights JavaScript SDK, which is not OpenTelemetry and never will be. The classic SDK 3.x releases are OpenTelemetry behind a `TelemetryClient` shim and are an interim step, not a destination. Any guide showing `TelemetryClient`, `TrackEvent`, `ITelemetryProcessor`, or `ITelemetryInitializer` as current practice is stale.
- **Instrumentation-key-only ingestion lost support 31 Mar 2025.** Connection strings (`APPLICATIONINSIGHTS_CONNECTION_STRING`) are required, and .NET SDK 3.x can fail at startup without one.
- **Classic (non-workspace) Application Insights resources retired 29 Feb 2024,** with automatic migration from May 2024. **Continuous export retired with them** and is incompatible with workspace-based resources; diagnostic settings (Storage / Event Hubs / partner) are the replacement. API keys survive migration but release annotations and the live metrics secure control channel need reconfiguring.
- **Availability tests: standard tests are the only current type.** Multi-step web tests retired 31 Aug 2024. URL ping tests retire **30 Sept 2026** and existing ones are deleted from resources. `TrackAvailability()` is archived classic API guidance. Standard tests are billed; ping tests were not.
- **Application Insights sampling is not adaptive sampling.** The Azure Monitor custom sampler decides at the end of span generation, hashes the trace ID, applies one rate to every telemetry type in a trace, and ignores upstream sampling decisions. Adaptive sampling is 2.x-SDK-and-Functions only (5 items/sec **per host**); .NET 3.x replaced it with `SamplingRatio` / `TracesPerSecond`; Java never had it. **Ingestion sampling now multiplies with SDK sampling** instead of standing down as it did under the classic SDKs.
- **Synapse SQL doc pages carry a Fabric successor notice** naming **Microsoft Fabric Data Warehouse** as the destination for new warehousing work, with an upgrade path and migration assistant for dedicated pools. Synapse is not retired and has no end date. Applies to every remaining guide that recommends Synapse.
- **Serverless SQL pool is read-only apart from CETAS.** No DML, no tables, no materialized views, no triggers; DDL is limited to views and security. It has no local storage, queries ADLS/Blob + **Cosmos DB analytical store + Dataverse** (never S3), reads Delta but **cannot write it or time travel**, has a **30-minute timeout that cannot be changed**, allows 100 databases and a 400 GB result set, and has **no result set caching**. Billing is *data processed* = storage reads + **uncompressed** intermediate transfer + CETAS writes, rounded up per MB with a **10 MB per-query minimum**, so `SELECT *` on a 1 TB Parquet table at 5:1 processes ~6 TB. Cost budgets (daily/weekly/monthly TB) reject the **next** query and never terminate the running one.
- **Dedicated SQL pool tables always have 60 distributions** (hash, round-robin, or replicated), fixed at creation; scaling changes nodes (~DWU/500), not distribution count. Concurrent queries cap at **128** and stop rising above DW6000c. Resource classes are static (`staticrc10`-`80`) and dynamic (`smallrc`/`mediumrc`/`largerc`/`xlargerc`, 3/10/22/70% at DW1000c+); Microsoft now points to **workload management** instead. **Materialized views are automatically and synchronously maintained** and used by the optimizer without being referenced. **Result set caching is dedicated-pool only, off by default**, 1 TB per database, and cache hits consume **no concurrency slots**.
- **Every current Azure Data Factory doc page carries the Fabric successor notice**, calling Data Factory in Microsoft Fabric "the next generation of Azure Data Factory" and directing new work there while offering existing estates an upgrade path. ADF is not retired and has no end date. Same framing obligation as row 21's Synapse-to-Fabric note.
- **ADF has exactly three integration runtimes and three trigger types.** Azure-SSIS IR is a **managed cluster of Azure VMs running the SSIS engine**, never Spark, and is unsupported in Synapse pipelines. Self-hosted IR is **Windows-only**, needs .NET Framework 4.7.2+ and a JRE, scales to **four nodes**, and makes outbound-only connections. IR precedence is self-hosted > managed-VNet Azure IR > global Azure IR, and either side of a Copy naming a self-hosted IR pulls the whole activity onto it. Triggers are schedule, tumbling window, and event-based (storage event + Event Grid custom event); **manual/on-demand execution is not a trigger type**. Only tumbling window supports backfill, retry, concurrency limits, and window variables, and only it waits for the pipeline run rather than reporting success at start.
- **ADF bills per *activity* run, not per pipeline run,** plus DIU-hours (copy on Azure IR) and vCore-hours (data flow execution **and debugging**). Data flow TTL is unavailable on the autoresolve IR. Per-pipeline billing is opt-in per factory and excluded from exported ARM templates.
- **Commitment discounts stack in a fixed order and only one of them is reversible.** Reservations apply **first** (more restrictive, up to 72% off), then the savings plan against its hourly commitment highest-discount-product-first (up to 65%, use-it-or-lose-it), then pay-as-you-go or the lower negotiated ACD rate. A **savings plan can never be cancelled or refunded**; a reservation is exchangeable for the same type and refundable up to **$50,000 in a rolling 12 months**. Reservations can be traded in for a savings plan, never the reverse. Utilization is computed over a best-fit **48-hour sliding window** and can transiently exceed 100%. There are now **two** savings plans: compute (1 or 3 year) and **databases (1 year only)**. Savings plans need EA, MCA, or MPA; other offer types get no discount.
- **No commitment discount covers licensing, storage, or networking.** A Reserved VM Instance covers VM compute only. Windows/SQL license cost comes off through **Azure Hybrid Benefit** (up to 80% Windows Server, up to 85% SQL Server), which needs core licenses with active Software Assurance **or qualifying subscription licenses**. AHB is centrally manageable at subscription/billing-account scope for **SQL Server only**; Windows Server stays resource-level. Reservation attributes are SKU, region **where applicable**, and scope, so VM reservations have **instance size flexibility but no region flexibility**.
- **Microsoft publishes commitment discounts as ceilings ("up to 72%"), never as per-service ranges.** Any table giving a per-service 1-year/3-year percentage band is fabricated precision.
- **Budgets never stop spending** ("resources aren't affected, and your consumption isn't stopped"), evaluate every 24 h on **actual (never amortized)** cost, and allow **5 thresholds and 5 email addresses** at 0.01-1000%. Budget **action groups work at subscription and resource group scope only**. **Cost anomaly detection is subscription-scope only**, free, 60-day forecast baseline, runs 36 h after the UTC day, max **5 anomaly alert rules per subscription**, unavailable in sovereign clouds.
- **The Cost Management connector for Power BI is in maintenance mode and no longer updated.** Microsoft moved Power BI guidance to **Exports**, which cover actual/amortized/**FOCUS**/price sheet/reservation details, recommendations, and transactions in CSV or Parquet. File partitioning is always on and cannot be disabled; read `manifest.json` rather than guessing file names.
- **Azure Automation lost two features to retirement on 31 Aug 2024,** both alongside the Log Analytics agent: **Update Management** (replaced by **Azure Update Manager**, a separate service with no Automation, Log Analytics, or AMA dependency, storing data in Azure Resource Graph and using per-resource RBAC) and the **agent-based Hybrid Runbook Worker** (agent-based jobs stopped **1 Apr 2025**; the extension-based V2 worker, installed through the VM extension framework with a system-assigned managed identity, is the only supported platform). **Azure Automation State Configuration retires 30 Sept 2027** and is replaced by **Azure machine configuration** delivered through Azure Policy; its Linux half retired 30 Sept 2023.
- **Azure sandbox limits:** three-hour **fair share** ceiling (not a shorter timeout), 400 MB memory, 1 GB temp disk, 1,000 sockets, max 10 jobs per sandbox, .NET Framework 4.7.2 only, and no executables, subprocesses, WMI, or elevation. Hybrid Runbook Workers are exempt from fair share entirely. Supported runbook runtimes are **PowerShell 7.6 / 7.4 / 5.1 and Python 3.10**; a webhook cannot start a Python runbook at all and misencodes input parameters for PowerShell 7.
- **Arc-enabled data services means SQL Managed Instance,** full stop. The PostgreSQL/Citus Hyperscale offering is no longer part of the product.
- **Logic Apps Consumption bills per action and, separately, per managed-connector call.** MS Learn gives no consistent connector count (400+ and 450+ appear on different pages), so don't assert one.
- **Microsoft Purview has two generations, and the classic one is closed.** **Data Catalog (classic)**, **Data Health Insights (classic)**, and **Purview Workflow (classic)**, the products previously branded Azure Purview, are no longer taking new customers and are in customer support mode. Their docs moved under `learn.microsoft.com/purview/legacy/`, which is the archive tell. The current experience is **Unified Catalog** in the Microsoft Purview portal (governance domains, data products, critical data elements, glossary terms, access policies, health controls, data quality, OKRs), running on top of the surviving **Data Map** (scanning, classification, lineage). Purview's own in-place **data sharing** for Blob and ADLS Gen2 was retired with support ending Sept 2025, replaced by Fabric external data sharing. Purview does **not** enforce row-level or column-level security, and a sensitivity label classifies without blocking.
- **Azure Databricks Standard tier is end-of-life.** Existing workspaces must move to Premium by **1 Oct 2026** and are upgraded automatically on that date. **Unity Catalog is enabled automatically for every workspace created after 9 Nov 2023** and has no pricing-tier requirement in the docs, so any "Unity Catalog needs a higher SKU" claim is stale. Managed tables use Delta **or Iceberg**.
- **Event Hubs retention is tier-bound:** Basic **1 day**, Standard **7 days**, Premium and Dedicated **90 days**. Partition count is fixed at creation on Basic/Standard (32 max); **dynamic partition scale-out is Premium/Dedicated only**. Capture is billed separately on Standard and included on Premium/Dedicated. Compaction is Standard+ (1 GB per partition on Standard, 250 GB above).
- **Fabric's workload list is Power BI, Databases, Data Factory, Industry Solutions, Real-Time Intelligence, Data Engineering, Data Science, Data Warehouse, and Fabric IQ (preview).** "Real-Time Analytics" is stale (now Real-Time Intelligence) and **Data Activator is not a separate workload** (it is **Activator**, inside Real-Time Intelligence). OneLake is built on ADLS Gen2, reaches external stores through **shortcuts** (ADLS, S3, GCS), and **virtualizes metadata between Delta and Iceberg in both directions** (Iceberg V2, source under 5,000 commits, 5 s to 2 min conversion latency). Governance is Purview plus the **OneLake Catalog**.
- **Column-level security is `GRANT SELECT ON table(cols)`, not encryption.** Any guide describing CLS as encrypting columns has confused it with **Always Encrypted**. Row-level security is an inline table-valued predicate function bound by a **security policy**, not a `WHERE` clause each query remembers to add.
- **The Azure Storage firewall has exactly four rule types:** virtual network rules (subnet + service endpoint), IP network rules (400 each), **resource instance rules**, and trusted-service/network-security exceptions. It does not filter by service principal.
- **ADLS Gen2 is not a service or account type.** It is Blob Storage with the **hierarchical namespace** enabled, so Blob features (tiers, lifecycle, immutability, redundancy) still apply. **ACLs cap at 32 entries per file and per directory** (about 28 usable), with access and default ACLs each getting their own 32, which is why ACL entries must hold Entra security groups. **Azure RBAC is evaluated before ACLs**, so a broad data-plane role assignment makes the ACL tree beneath it moot.
- **Azure Stream Analytics is not a simple-queries-only engine.** Submillisecond latency on the Trill engine, exactly-once processing with at-least-once delivery, and a query language covering pattern matching, geospatial functions, and anomaly detection, extensible with JavaScript/C# UDFs and aggregates and Azure ML function calls. It also runs on IoT Edge and Azure Stack.
- **The Confluent offering is "Apache Kafka & Apache Flink on Confluent Cloud",** an **Azure Native Integration** provisioned through the `Microsoft.Confluent` resource provider, not a plain Marketplace listing.
- **NSG flow logs retire 30 Sept 2027 and can no longer be created.** Traffic Analytics on them ends and the NSG flow log resources are deleted (Storage records remain). Replacement is **VNet flow logs**; D/E/F v6 VM families support only those.

- **Power BI Premium per-capacity P SKUs are retiring.** New P SKUs are no longer sold and each subscription ends at its agreement term; EA customers with an active agreement can renew existing capacity until the EA term ends. Replacement is Fabric **F SKUs** (P1 to F64, P2 to F128, P3 to F256, P4 to F512, P5 to F1024). Lapse means a 30-day grace period, throttling from day 31, and all operations rejected from day 91. **Pro, PPU, and the EM/A embedding SKUs are NOT part of this retirement.** Autoscale does not exist on F SKUs (on-demand resizing replaces it), and billing moves from M365 commitment to Azure. Any guide recommending "Power BI Premium capacity" needs rewriting.
- **F64 is the free-viewer threshold.** On F64 and larger, a free license plus the Viewer role can consume content. On F2-F32 every viewer still needs Pro or PPU. Headcount rules of thumb ("100+ users justifies capacity") are fabricated; this boundary is the real one.
- **Semantic model size is a licensing limit, not an engine limit:** shared capacity/Pro 1 GB (plus a 10 GB cap on uncompressed data processed during refresh, 8 scheduled refreshes/day), PPU 100 GB (48/day), Fabric F2-F8 3 GB, F16 5, F32 10, F64 25, F128 50, F256 100, F512 200, F1024+ 400. Refresh roughly doubles the footprint. A 225-second visual render timeout applies on every SKU.
- **Power BI real-time streaming is retiring.** Creation of push, streaming, and PubNub semantic models and streaming data tiles stays enabled until **31 Oct 2027**, then stops; existing models are unaffected. Replacement is Fabric Real-Time Intelligence. The three types differ: push writes to a real database (1 req/sec, 16 MB/req, 1M rows/hour) and supports full reports; streaming holds about an hour in a temporary cache with no database and only custom streaming tiles; PubNub stores nothing. Azure Stream Analytics output uses pushStreaming with a 200,000-row basicFIFO policy. Automatic page refresh is DirectQuery-only.
- **Gateway names changed.** The current set is **on-premises data gateway** (standard mode, multi-user, all supported services, clusterable), **on-premises data gateway (personal mode)** (single user, Power BI only), and **virtual network (VNet) data gateway** (Microsoft-managed, no install, connects to sources secured by an **Azure VNet, not on-premises**). "Personal Gateway" and "Enterprise Gateway" are stale labels. Limits: 1,000 data sources per cluster, 16 MB uncompressed DirectQuery response, roughly 5-hour credential cache, only the last six monthly releases supported.
- **Dataflow Gen1 is legacy** and "won't receive new feature investment"; Gen2 (Fabric Data Factory) is the recommended path for customers with Fabric capacity, writing Delta to Fabric destinations. Gen1 output is Common Data Model format in Power BI storage or a bring-your-own ADLS Gen2 account. Pro/PPU customers without Fabric stay on Gen1.
- **Endorsement has three badges, not two:** Promoted (any user with write permission), Certified (only users a Fabric admin designates; delegable per domain), and **Master data** (admin-designated users, data-bearing items only). Certification and master data must be enabled at the tenant. Every Fabric/Power BI item **except Power BI dashboards** can be promoted or certified.
- **A sensitivity label classifies; a Purview protection/publishing policy enforces.** A label does not by itself block export. Labels propagate downstream and survive supported export paths (Excel, PDF, PowerPoint, Analyze in Excel, .pbix download) but **not CSV/TXT export or cross-tenant access**. Blocking Excel export is a tenant setting.
- **Deployment pipelines take 2 to 10 stages (default 3: Development, Test, Production), work by item pairing, and have no rollback.** Git integration is the versioning mechanism. Deployment rules swap data sources and parameters per stage. From **12 Feb 2026** pipelines dropped support for semantic models not upgraded to Enhanced Metadata.
- **User-defined aggregations require the detail table to be in DirectQuery storage mode**, not Import. Aggregation tables are hidden and hit transparently; a Precedence value orders multiple aggregations. RLS must filter both the aggregation and the detail table (filtering only the aggregation is rejected outright). Automatic aggregations is a separate capacity feature.
- **The monitoring app is the Microsoft Fabric Capacity Metrics app** (supersedes the Premium metrics app). Pages: Health, Compute (14 days), Storage (30 days), Timepoint (30-second intervals). Data lands 10-15 min behind, it has **no alerting** (use Fabric capacity events), and it does not support PPU.
- **Paginated reports no longer require Premium.** Licensing matches Power BI reports: free license publishes to My Workspace, Pro/PPU elsewhere with at least Contributor. Authored in **Power BI Report Builder** (free download), no underlying data model, exports to Excel/Word/PowerPoint/PDF/accessible PDF/CSV/XML/MHTML, and cannot be pinned to dashboards.

Secret-based options remain only for backwards compatibility. A group approver needs only one member to approve, and an approval timeout marks the stage **skipped**. Evaluate artifact is container images only. ServiceNow Change Management is a marketplace extension.

Rolling is **VM resources only**, and blue-green is not a built-in strategy. Deployment jobs do not clone the repo (`checkout: self` needed), auto-download artifacts only in the `deploy` hook, and retrying a rolling stage re-runs on every VM. Any guide saying Azure DevOps has no built-in deployment strategies is wrong.

Only **succeeded and partially-succeeded** runs are retained by policy. Deleting a run deletes its logs, artifacts, symbols, test results, and Sources-task tags. Longer retention comes from marking a run for indefinite retention or setting a lease via the Lease API.

They are already scoped per project, pipeline, and branch, so branch identifiers in a cache key are counterproductive: the source branch reads and writes its own scope, `main`/`master` are read-only to other branches, and a PR run writes only to `refs/pull/N/merge`. Invalidate by versioning the key. Self-hosted agents need GNU tar (Windows/Linux) or BSD tar (macOS) on PATH.
- **Managed DevOps Pools supersedes Azure VM Scale Set agent pools** for autoscaling self-hosted capacity, running the VMs in a Microsoft-managed subscription. VMSS agent pools still work: Azure Pipelines does the scaling (the scale set's own autoscale and overprovisioning must be disabled), samples every 5 minutes, and can reimage after every job. Ubuntu, Windows Server, and Windows 10 client only, no macOS, Azure public cloud only.

Creator is project-level only, and **User carries the ability to manage that resource's approvals and checks**. Pipeline permissions are a separate axis from user permissions, and "Open access" requires Project Administrator and should stay off for anything holding a secret.

- **Azure Artifacts storage is 2 GiB free per organization, and hitting the cap stops publishing.** Upstream-saved packages and the 30-day recycle bin both count toward billed storage; **pipeline artifacts and pipeline caching do not**. Retention policies **exempt packages promoted to a view**. Package versions are immutable and deleting one does not free the version number. Supported formats are NuGet, npm, Maven, Python, **Cargo**, and Universal (500 MiB per file, 4 TiB for Universal; 5,000 versions per package ID; npm *package.json* capped at 375 KB).
- **Azure Artifacts has four feed roles**: Feed Reader, **Feed and Upstream Reader (Collaborator)**, Feed Publisher (Contributor), Feed Owner. Collaborator is the role that permits saving a package from an upstream source, and build identities (`[Project] Build Service` and `Project Collection Build Service`) get it by default. Publishing needs Feed Publisher granted explicitly. Any three-role Reader/Contributor/Administrator list is wrong.
- **Upstream resolution order is fixed**: packages published directly to the feed, then packages already saved from an upstream, then upstream sources in configured order. That is the dependency confusion defense, and it only holds if the client config names one feed (NuGet needs `<clear />`). You **cannot publish a version that already exists** in an enabled upstream; override by disabling the upstream, publishing, re-enabling. Custom upstreams are npm-only. Public-registry packages take 3-6 hours to appear.
- **Feed views: @Local is the default and holds everything**, both packages published to the feed and packages saved from upstream. @Prerelease and @Release are suggested, empty, renameable and deletable. **Access to a view grants download access through that view even without direct feed access.**
- **Azure DevOps auditing is public preview, off by default, and Microsoft Entra-backed organizations only.** Organization-level, 90-day retention, unavailable on Azure DevOps Server. It records state changes (permissions, policies, deletions, PAT lifecycle), **not** commits, PR approvals, or package downloads. It does not log sign-in events or Entra group membership changes. Longer retention needs export or audit streaming to a SIEM. There is no "Activity page".
- **Azure Repos has repository policies distinct from branch policies**: commit author email validation, file path validation, case enforcement, reserved names, maximum path length, maximum file size. All default Off, settable at **All Repositories** (which becomes the default for repos created later) or per repository. They reject a push; branch policies gate a merge.
- **The seven branch policies are** minimum reviewers, check for linked work items, check for comment resolution, limit merge types, build validation, status checks, and automatically included reviewers. **There is no branch naming policy** (naming is enforced with branch folder permissions). Setting any policy auto-requires pull requests and makes the branch undeletable. **Cross-repo policies** protect each repo's default branch or a case-sensitive branch-name pattern across a project, including branches that do not exist yet. Override needs the *Bypass policies when completing pull requests* permission.
- **Code search requires the Marketplace Code Search extension and indexes only the default branch**, plus up to five more branches added per repository. It is text and code-structure search, not semantic.
- **TFVC is "feature complete", not deprecated.** Git is the default for new projects and receives all future investment, Microsoft maintains TFVC compatibility with no end date, and the two can coexist in one project. TFVC server workspaces scale to millions of files and large binaries without Git-LFS, which is the actual reason it persists. Migration tool is git-tfs.
- **Secret scanning, push protection, dependency scanning and code scanning are paid add-ons**, now sold as two standalone products: **GitHub Secret Protection** (secret scanning, push protection, security overview) and **GitHub Code Security** (dependency scanning, CodeQL code scanning, security overview).
- **PATs are always tied to the user who created them**, and service principals and managed identities cannot create or manage them. Org policies can restrict full-scoped PATs, restrict global PATs, and enforce a maximum lifetime. On Entra-backed orgs a PAT goes inactive without a full sign-in within 90 days. Leaked PATs on public GitHub are auto-revoked. **Azure Artifacts does not accept a PAT as a NuGet API key** (use the Azure Artifacts Credential Provider locally, NuGet Authenticate task in pipelines). Microsoft's recommended order is Entra tokens, managed identities/service principals, then PATs as a last resort.

- **GitHub Actions OIDC**: issuer `https://token.actions.githubusercontent.com`, audience `api://AzureADTokenExchange`, and the workflow needs `permissions: id-token: write`. Subject formats are `repo:ORG/REPO:ref:refs/heads/<branch>`, `repo:ORG/REPO:ref:refs/tags/<tag>`, `repo:ORG/REPO:pull_request`, and `repo:ORG/REPO:environment:<name>`. **Repositories created after 15 July 2026 default to an immutable subject** embedding owner and repo IDs (`repo:OWNER@OWNER-ID/REPO@REPO-ID:ref:...`); existing repos keep the old format unless they opt in, and it is unavailable on GHES. **`azure/login` is at v3** (not v1 or v2), with `auth-type` of `SERVICE_PRINCIPAL` (default) or `IDENTITY` for managed identity on self-hosted runners; the legacy path passes an `AZURE_CREDENTIALS` JSON blob via `creds`.
- **Federated identity credential limits (applies to Azure DevOps service connections too)**: **maximum 20 per app registration or user-assigned managed identity**, exactly one audience, **no wildcards in any property**. A wrong subject creates successfully and then fails the token exchange **with no error**. Propagation takes minutes; `AADSTS70021: No matching federated identity record found for presented assertion` right after creation is replication lag. Only RS256 issuers are supported, and concurrent FIC creation under one user-assigned managed identity returns 409.
- **`Azure/bicep-action` does not exist.** The current action is **`Azure/bicep-deploy`** (Bicep and ARM, what-if, and first-party **deployment stacks** support); `Azure/arm-deploy` is the predecessor and Azure directs new work away from it. This is the action to name for the deployment-stacks-over-complete-mode point.
- **GitHub environment protection rules**: required reviewers up to **6 people or teams, and only one needs to approve**; wait timer; deployment branch policy (all branches, protected branches, or selected branches and tags by name pattern); custom rules from GitHub Apps; and an org control to disallow bypassing. **Environment secrets are released only after every rule passes.** GitHub publishes no evaluation order among the rules, so don't assert one.
- **Reusable workflow limits**: **ten levels** of nesting (caller plus nine), no circular references, secrets pass only between **directly connected** workflows, `secrets: inherit` works only within the same org or enterprise, and **`on: workflow_call` does not support the `environment` keyword** so a reusable workflow cannot declare an environment. Referenced by commit SHA (recommended), release tag, or branch, and a tag beats a same-named branch.
- **GitHub Actions billing is elapsed minutes weighted by OS**, not concurrency: Free 2,000 min/month with 500 MB artifact storage, Team 3,000 / 2 GB, Enterprise Cloud 50,000 / 50 GB, 10 GB cache on all. Standard runners are **free for public repositories**. Windows costs roughly 1.7x Linux and macOS roughly 10x. **Larger runners are always billed, including on public repos, and never draw on included minutes.**
- **GitHub's action-pinning guidance is a full-length commit SHA, full stop** ("the only way to use an action as an immutable release"). Tags are acceptable only for trusted or Marketplace-verified creators. Any "use SHAs for critical actions and tags for the rest" advice contradicts it. Related: set the `GITHUB_TOKEN` default to read-only contents and raise per job, and **never attach a self-hosted runner to a public repository** (GitHub: "should almost never be used").
- **Script injection is the GitHub Actions vulnerability class to name.** Interpolating {% raw %}`${{ github.event.* }}`{% endraw %} (PR title, branch name, issue body) into a `run` step executes attacker text on the runner. Mitigations are binding the value to an `env` variable and referencing it as a shell variable, or passing it as an action input.

- **Azure ML built-in roles are AzureML Data Scientist, AzureML Compute Operator, and AzureML Registry User**, plus generic Owner/Contributor/Reader. Data Scientist covers everything in a workspace *except* creating or deleting compute and modifying the workspace. There is no "ML Workspace Owner", "MLOps Engineer", or "Inference Operator" built-in role. Workspaces created after **19 Nov 2024** assign the system-assigned managed identity the narrower **Azure AI Administrator** role on the resource group instead of Contributor.
- **An Azure ML compute cluster has a single VM size fixed at creation.** CPU and GPU nodes cannot be mixed in one cluster; assign compute per pipeline node or use serverless with a per-node instance type. **Serverless compute is Azure ML managed compute, not AKS or ACI**, and Microsoft now recommends it over creating a cluster. Compute instances have a 120 GB OS disk, support idle shutdown, and still bill for disk, public IP, and load balancer while stopped.

The workspace default storage account **cannot** be type BlobStorage, premium, or have **hierarchical namespace enabled**, so an ADLS Gen2 account cannot be the workspace storage (attach it as a datastore instead). A workspace cannot be moved to another subscription.
- **The Azure ML model registry has no promotion stages and no approval workflow.** It offers name + auto-incrementing version, tags, and lineage (training job, deployment location, deployment health). Promotion is built with tags plus CI/CD, or by moving assets through an **Azure ML registry** (the cross-workspace/cross-region asset store, distinct from the workspace model registry). A registered model in an active deployment cannot be deleted. Any guide describing dev/staging/prod stages in the Azure ML registry is wrong.
- **SDK v2 pipeline code**: `from azure.ai.ml.dsl import pipeline` then `@pipeline(...)`; components use `from mldesigner import command_component` then `@command_component(...)`, or YAML loaded with `load_component()`. **`@dsl.command` does not exist.**

Online endpoints come in two forms: **managed online endpoints** (Azure ML serverless infrastructure) and **Kubernetes online endpoints** (attached AKS/Arc). Multiple deployments behind one endpoint with percentage traffic splitting is the safe-rollout mechanism. - **Azure ML model monitoring has six signals**: data drift, prediction drift, data quality, feature attribution drift (preview), model performance (preview), and generative AI generation safety and quality (preview). It needs production inference data, collected **automatically only on managed online endpoints** (model data collection); batch endpoints and external deployments require you to collect it. Configured with lookback window size and offset (windows must not overlap). Runs on Spark, so avoid `MLTable`, and it **does not support the `AllowOnlyApprovedOutbound` managed VNet setting**.

"Forecast explanations" is not a component. Speaker recognition and Custom Commands are absent from it, which is how the retirements read on the current page.

Formats: RIFF WAV, 8 or 16 kHz, mono, 16-bit PCM, zip under 2 GB or 10,000 files. - **SSML value semantics**: a bare percentage on `prosody` is **relative**, absolute `volume` runs 0.0-100.0 (MS names "a volume of 120" as its own example of an unsupported value), absolute `pitch` is in Hz, `rate` takes a bare multiplier. Pitch changes should stay within 0.5-1.5x and rate within 0.5-2x. **Emotion is `mstts:express-as`** (`style`, `styledegree` 0.01-2, `role`), not a `prosody` attribute. There is no "voice mixing"; layering means multiple `<voice>` elements. HD voices, personal voices, and embedded voices each support a **narrower** SSML set than standard voices.

With GStreamer on the system path the SDK accepts MP3, OPUS/OGG, FLAC, ALAW and MULAW in WAV containers, and `ANY` for MP4/unknown. The **JavaScript, Objective-C, and Swift SDKs do not support compressed audio at all**. AAC is not in the SDK list (fast transcription's file-upload list is wider and does include it).

- **Published Azure RPO/RTO figures, for use instead of remembered ones.** SQL Database: zone redundancy RTO typically <30 s with **RPO 0**; failover groups (customer-managed) or active geo-replication RTO typically **<60 s**, RPO >= 0; geo-restore RTO and RPO both minutes to hours. Cosmos DB RPO by configuration: single region any consistency **<240 min**; multi-region single-write **Strong = 0**; Bounded staleness = the configured K and T (multi-region floor **100,000 writes or 300 s**); Session/Consistent prefix/Eventual **<15 min**. Azure Storage publishes **no general geo-replication RPO** — the 15-minute figure belongs only to **Geo priority replication for block blobs**; otherwise **Last Sync Time** is the measurement. - **Azure Storage redundancy facts.** Durability: LRS >=11 nines, ZRS >=12, GRS/GZRS >=16. The **secondary is always LRS** whichever geo option you pick; GRS and GZRS differ only in the primary. Read availability >=99.9% for GRS/GZRS and **>=99.99% for RA-GRS/RA-GZRS**; Microsoft recommends **RA-GZRS**. GZRS needs a region with **both** availability zones and a paired region. **Azure Files does not support RA-GRS or RA-GZRS**; **managed disks support only LRS and ZRS** (no geo option at all); the **archive tier is unsupported on ZRS, GZRS, and RA-GZRS**. Redundancy is an account-level setting shared by every service in the account.
- **Azure Site Recovery Azure-to-Azure is not agentless** — the Mobility service extension is installed on the VM automatically; ASR never needs inbound connectivity. Replication policy defaults: **recovery point retention one day**, and **app-consistent snapshot frequency zero hours, meaning disabled**. Crash-consistent recovery points are every **5 minutes and cannot be modified**. App-consistent snapshots use VSS **Copy Only (`VSS_BT_COPY`)**, so they don't disturb SQL log backup chains. Multi-VM consistency uses replication groups communicating over **port 20004** and affects performance. Target resources get an `asr` suffix and replica disks an `-ASRReplica` suffix; the replica takes the **same availability zone number** as the source. The **availability type (single/set/zone) cannot be changed** without disabling and re-enabling replication.
- **Azure SQL Database backup cadence:** full weekly, differential every 12 or 24 hours, transaction log every 5-10 minutes, stored in geo-redundant backup storage for **7 days by default**, with PITR configurable up to **35 days** on every tier except Basic. A geo-secondary used **only** for DR can be designated a **license-free standby replica**.
- **Cosmos DB strong consistency costs beyond latency.** Writes must commit in **every** region, so write latency is 2x the RTT between the two farthest regions plus 10 ms at p99, and strong is **blocked by default beyond 5,000 miles / 8,000 km** (support request required). Strong and bounded staleness reads consult two replicas, so their **RU cost is double** and read throughput at a given provisioning is half. Accounts with 3+ strong-consistency regions use **dynamic quorum**, dropping unresponsive regions (which then cannot serve reads) to preserve write availability.
- **Azure region pairing guarantees far less than it is read to guarantee.** Learn states regions are independent and only *a small number* of services use pairs. A pair provides exactly three things: region recovery sequence, sequential (staggered) platform updates, and *almost all* pairs sitting in the same geography. It explicitly provides **no** automatic resilience, HA, DR, or failover. Pairing is **not always reciprocal or same-geography**: Brazil South pairs to South Central US (outside the Brazil geography, one-way), West India pairs to South India while South India pairs to Central India, and West US 3 pairs one-way to East US. Nonpaired regions (Chile Central, Mexico Central, Austria East, Belgium Central, Denmark East, Italy North, Poland Central, Spain Central, Israel Central, Qatar Central, Indonesia Central, Malaysia West, New Zealand North) use availability zones instead. **The "at least 300 miles apart" figure is not on the current page** — don't assert it.
- **Azure Storage has three failover types with very different outcomes.** Customer-managed **planned** (GA): no expected data loss, primary and secondary swap, account converts to GRS and **geo-redundancy is retained** — this is the DR-drill mechanism. Customer-managed **unplanned**: data loss expected, the original primary's copy is **deleted**, and the account converts to **LRS** with geo-redundancy lost; re-enabling GRS costs a full re-replication and archived blobs must be rehydrated first. **Microsoft-managed**: region-wide, extreme circumstances only, not invocable per account, and Learn says explicitly **do not** rely on it. Failover typically completes in under an hour. **Last Sync Time** is the RPO estimator. - **SQL Database failover-group policy names invert the plain-English meaning.** `manual` is the **customer-managed** policy and is Microsoft's recommendation; `automatic` is the **Microsoft-managed** policy, which triggers a **forced** (data-losing) failover for **every** group in the region on that policy, no sooner than `GracePeriodWithDataLossHours`, which **cannot be set below one hour**. **Both policies can lose data.** Planned **Failover** fully synchronizes first and guarantees no data loss, but needs a reachable primary; **Forced failover** does not. - **ACR registries run in one of two role assignment permissions modes.** "RBAC Registry + ABAC Repository Permissions" uses `Container Registry Repository Reader`/`Writer`/`Contributor` (ABAC-scopable) plus `Container Registry Repository Catalog Lister` (**not** ABAC-scopable, and the repository roles deliberately grant no catalog list). "RBAC Registry Permissions" is the legacy mode with registry-wide `AcrPull`/`AcrPush`/`AcrDelete`/`AcrImageSigner`. `az acr login` comes from the control-plane role `Container Registry Contributor and Data Access Configuration Administrator`, which grants **no** data-plane access.
- **Container image vulnerability assessment is Microsoft Defender Vulnerability Management (MDVM) via Defender for Cloud, not a registry SKU feature.** It covers ACR, ECR, GAR, GCR, and configured external registries. New images are scanned **within a few hours**, and a **daily rescan** covers only images pushed or pulled in the last 30 days or currently running in a monitored cluster; anything outside that window stops being reassessed. OS packages are covered on Linux and Windows, **language packages on Linux only**. Runtime assessment excludes Windows nodes and AKS ephemeral OS disks.
- **ACR cleanup is three separate mechanisms.** The **retention policy** covers **untagged manifests only** and is Premium-only. Tag-pattern deletion is **`acr purge` run as an ACR Task**. **Soft delete** is a separate policy giving a recovery window. Any guide describing the retention policy as deleting by tag pattern or keeping the last N images has conflated it with `acr purge`.
- **Deployment slots by plan: Consumption 2, Premium 3, Dedicated 1-20, Container Apps none (revisions instead), and Flex Consumption none at all.** Flex uses rolling site updates for zero-downtime deploys. A slot swap is explicitly **not** a zero-downtime guarantee: in-flight executions can be terminated and scaled-out apps can see degraded availability. Trigger and binding settings must be marked sticky before the first swap; VNet integration, hybrid connections, service endpoints, and private endpoints never swap.
- **Functions retry policies cover only four triggers: Cosmos DB, Event Hubs, Kafka, and Timer.** Service Bus, Queue Storage, and Blob Storage retry through the binding extension (`maxDequeueCount` default 5 then the poison queue; Service Bus via host.json on extension 5.x or max delivery count on older ones), and Event Grid retries at the event subscription. A retry-policy attribute on a Service Bus or Queue trigger does nothing. Retry counts live in instance memory, so an instance failure resets them.
- **Service Bus trigger concurrency defaults: `maxConcurrentCalls` 16 multiplied by the instance's core count, `maxConcurrentSessions` 8, `maxMessageBatchSize` 1,000.** The 1,000 is the batch size, not a concurrency limit. Dynamic concurrency (`dynamicConcurrencyEnabled`) is off by default, covers Blob/Queue/Service Bus only on 5.x extensions, and starts each function at a concurrency of one.
- **Durable Functions storage backends are Durable Task Scheduler (recommended, managed), Azure Storage (default), MSSQL, and Netherite.** There is **no migration path between backends**. Netherite support ends **31 March 2028** and it is unsupported on Flex Consumption; MSSQL does not support entities on .NET isolated. Isolated-model Durable APIs: `[Function]`, `[OrchestrationTrigger] TaskOrchestrationContext`, `context.GetInput<T>()`, `CallActivityAsync<T>`, `WaitForExternalEventAsync<T>`, `TaskOptions.FromRetryPolicy(new RetryPolicy(...))`, `[EntityTrigger] TaskEntityDispatcher` with `TaskEntity<TState>`, and `[DurableClient] DurableTaskClient` with `ScheduleNewOrchestrationInstanceAsync`. Entity interface proxies are in-process only.
- **Azure Functions has no published cold start durations.** MS Learn documents only which plans scale to zero and what mitigates it (always-ready instances on Flex Consumption and Premium, Always On for Dedicated, minimum replicas on Container Apps). Every per-language or per-plan duration figure traces to third-party benchmarks or Q&A threads. Don't assert one.
- **The blob trigger has two implementations and the default is the slow one.** `LogsAndContainerScan` (default) polls storage logs and can lag up to 10 minutes on an idle Consumption plan; `EventGrid` is recommended and is the **only** blob trigger Flex Consumption supports.
- **Logic Apps hosting is Consumption, Standard (Workflow Service Plan), Standard on ASEv3, and Standard hybrid** (on-premises via an Azure Container Apps extension). Integration Service Environment is gone from the docs entirely — don't name it.
- **API Management has eight tiers**, in two generations: Consumption, Developer, Basic, Basic v2, Standard, Standard v2, Premium, Premium v2. Multi-region deployment and the self-hosted gateway are **Premium (classic) only** and absent from Premium v2. Consumption has no built-in cache and no VNet support.
- **Azure Static Web Apps has exactly two preconfigured auth providers**, GitHub and Microsoft Entra ID. X (formerly Twitter) was removed after an API policy change, and registering a custom provider disables all preconfigured ones.
